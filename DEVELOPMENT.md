# Developing BetterReplay

How to build BetterReplay, how it works, and what's still unverified. For installing and using it, see [README.md](README.md).

> **Status: early testing.** The platform-independent core has 227 unit tests and the module builds and links against the MSFS 2024 SDK. In-sim test runs have led to the playback fixes for airspeed, gear, throttle, flaps and reverse described below. The control setup has run in the sim and set up all four controls on the PMDG 777 and 737, the iniBuilds A350 and A380, the Synaptic A220 and the FSS E190 (its spoilers taken as automatic), the A350's gear above the runway without a takeoff. Findings below on the A320neo V2 and the CJ4 are from older versions and still to be retested. Which aircraft have been tested and the known issues are in the README ([Aircraft](README.md#aircraft), [Known issues](README.md#known-issues)). Work through [MANUAL_TEST.md](MANUAL_TEST.md) and see [Known gaps](#known-gaps).

## Requirements

| | |
|---|---|
| MSFS 2024 | Steam or Microsoft Store |
| MSFS 2024 SDK | Core 1.7.3 or later, with `MSFS2024_SDK` set (the installer does this) |
| Visual Studio 2022 or Build Tools 2022 | C++ workload (MSBuild, v143), for the native unit tests |
| Node.js 22.13+ or 24 | Builds the panel (built-in TypeScript type stripping, no npm packages) |
| *Optional:* the MSFS2024 platform toolset | Builds the module from the VS solution. Without it, `build.ps1` calls the SDK's clang directly. |

## Build and install

```powershell
# First build: also compiles the toolbar panel definition (.spb).
# Close the sim first: fspackagetool starts FlightSimulator2024.exe in package-builder mode.
.\build.ps1 -Package

# Later builds reuse the cached .spb (package\spb\), and -Install copies into your Community folder.
.\build.ps1 -Install
```

| Option | |
|---|---|
| `-Configuration Debug` | Unoptimized module with debug info and verbose logging |
| `-SkipTests` | Skip the native core tests |
| `-Package` | Run `fspackagetool` to (re)build the panel `.spb`. Needed once, and again whenever `package\PackageSources\InGamePanels\InGamePanel_BetterReplay.xml` changes. |
| `-Install` | Copy `dist\Community\betterreplay-recorder` into the Community folder (found via `UserCfg.opt`) |
| `-CommunityPath <dir>` | Install somewhere else |
| `-Zip` | Also zip the package for a GitHub release (see [Releasing](#releasing)) |

The output is `dist\Community\betterreplay-recorder`. To install by hand, copy that folder into your Community folder. On Steam it's `%APPDATA%\Microsoft Flight Simulator 2024\Packages\Community` unless you moved it.

If the `.spb` hasn't been built, the recorder still runs and saves clips, but the toolbar panel won't appear. `build.ps1` warns about this.

`-Package` needs Steam to agree that MSFS 2024 isn't running. If a previous sim instance ended abnormally (crash, or killed in Task Manager), Steam can keep its "running" flag, and then it refuses with *"game is already running"*. `build.ps1` checks for this first. To clear it, click **Stop** on MSFS 2024 in your Steam library, or exit Steam completely and restart it.

You can also build the package in DevMode: **File → Open project…** → `build\package\BetterReplay.xml` (created by `build.ps1`) → **Build**.

## Releasing

Releases are built locally and published on GitHub in the browser.

1. **Set the version** (`major.minor.patch`) in two places: `Version` in `package\PackageDefinitions\betterreplay-recorder.xml` and `kVersion` in `src\module\Module.cpp`. To ship the control profiles you've set up, run `node tools\export-profiles.mjs` (see [Tests and tools](#tests-and-tools)). Commit and push.
2. **Build the zip:** `.\build.ps1 -Zip`. It writes `dist\betterreplay-recorder-<version>.zip`, holding the `betterreplay-recorder` folder ready to extract into Community. It stops before building if the two versions differ or the compiled panel is missing or out of date (then run `.\build.ps1 -Package -Zip` with the sim closed). It warns if there are uncommitted or unpushed changes, or if the version's tag is already on another commit.
3. **Publish:** open the link it prints. That's GitHub's new-release form, with the tag (`v<version>`), the commit you built and the title filled in. Add release notes, drag in the zip and choose **Publish release**. Publishing creates the tag. While BetterReplay is in early testing, tick **Set as a pre-release**.

Before publishing, install from the zip itself to check it: extract it into your Community folder in place of your dev build, and start the sim.

## Tests and tools

- **Tests:** `.\build.ps1` builds and runs them. To run a subset: `build\tests\Release\CoreTests.exe Detector_`. The detector tests replay synthetic traces from `tests/TraceGen.h`: normal takeoff, landing, bounce, touch-and-go, spawn on runway, spawn airborne, and a pause mid-landing.
- **Panel without the sim:** run `.\build.ps1 -SkipTests`, then `node tools\panel-harness.mjs` and open http://localhost:8077/. It serves the built panel with the MSFS globals mocked and a fake recorder behind CommBus.
- **Module check:** `tools/check-wasm.mjs` runs after every module build. It fails if a required MSFS 2024 export is missing or the module imports something unexpected.
- **VS solution:** `BetterReplay.sln` has `CoreTests` (x64) and `BetterReplayModule` (MSFS|MSFS2024). The module project only loads once the MSFS2024 platform toolset is installed.
- **In-sim checklist:** [MANUAL_TEST.md](MANUAL_TEST.md), with the log lines to expect at each step.
- **Exporting control profiles:** `node tools\export-profiles.mjs` copies the profiles in your [work folder](#work-folder)'s `aircraft.json` into `profiles\`, one file per aircraft, named after the last part of its key (`profiles\pmdg-777.json`; `title-<title>.json` for an aircraft known only by its title). A file is matched to its aircraft by the `key` inside it, so you can rename it. The work folder's profile replaces the file's unless the file's is newer, and files for aircraft the work folder doesn't have are left alone (delete one to drop that aircraft). Profiles with nothing set up aren't copied, and "never for this aircraft" isn't kept. `--from <folder or file>` reads another work folder or `aircraft.json`. `build.ps1` combines the files into one, the package's `profiles\aircraft.json` (`tools\pack-profiles.mjs`), and stops if a file isn't a profile or two files are the same aircraft. See [Included profiles](#included-profiles) for how the module uses them.
- **Inspecting a clip** outside the sim:

  ```powershell
  node tools\rpl-dump.mjs <clip.rpl>                  # header + a sample row per second
  node tools\rpl-dump.mjs <clip.rpl> --csv clip.csv   # every frame, every channel
  node tools\rpl-dump.mjs <clip.rpl> --cols gs,thr_1,rev_1,rnoz_1 --every 15   # chosen channels, every 0.5 s
  ```

## Configuration

All detection thresholds are in `DetectorConfig` in [src/core/EventDetector.h](src/core/EventDetector.h). The sample rate, buffer length, retention count and the longest Stop keeps the aircraft frozen are in `EngineConfig` in [src/core/Engine.h](src/core/Engine.h). Rebuild after changing them.

Two detector rules go slightly beyond the original spec:

- `landingMinAirborneSec = 5`: a touchdown only counts as a landing after at least 5 s airborne, so skips on the takeoff roll aren't "landings".
- `holdOffNewEventsAfterPause = false`: after a pause, detection only re-arms if the aircraft moved while paused. Otherwise a pause on short final would lose the landing. Set it to `true` for the strict "re-arm after every pause" behaviour.

## How it works

```
 Toolbar panel (HTML/TS)            WASM module (C++)
 ┌──────────────────────┐ CommBus  ┌───────────────────────────────────────────────┐
 │ stateless remote     │ ───────► │ CommBridge   JSON commands / replies           │
 │ polls status at 4 Hz │ ◄─────── │ Engine       ring buffer, detector, library,  │
 └──────────────────────┘          │              playback   (src/core, no SDK)    │
                                   │ SimBridge    SimConnect: per-frame data,      │
                                   │              events, freeze, SetData          │
                                   │ FileStore    \work stdio I/O                   │
                                   └───────────────────────────────────────────────┘
```

The recorder is a standalone WASM module. It keeps a 10-minute ring buffer at 30 Hz (about 12 MB) and runs whether or not the panel is open.

- **`src/core/`** is plain C++17 with no SDK dependencies. It holds:
  - the data-driven channel table (`Channels.cpp`)
  - the ring buffer, event detector, clip format and clip index (`index.json`)
  - interpolation, the playback controller, and the `Engine` that ties them together

  It builds natively for the unit tests and into the WASM module.
- **`src/module/`** is the thin SDK adapter: SimConnect (`SimBridge`), CommBus (`CommBridge`), the work folder (`FileStore`), and the entry points (`Module.cpp`: `module_init`, `module_post_sim_systems_update`, `module_deinit`).
- **`src/panel/`** is the toolbar panel. The TypeScript is stripped to JavaScript at build time (`tools/strip-types.mjs`).
- **`package/`** holds the package definition, the panel definition and the toolbar icon.

**Channels.** Each channel is one row in `kChannels`: simvar, units, storage type, interpolation and playback mode. That row drives the SimConnect definitions, the file format and playback. Add a row to record more.

**CommBus protocol.**
- Commands go to `BetterReplay.Cmd` as JSON: `{"op": …, "id": n}`.
  - `status`
  - `clips{offset}` (20 per page)
  - `play{file}`, `pause`, `resume`, `seek{t}`, `speed{x}`, `stop`
  - `delete{file}`, `saveLast`
  - `setupStart`, `setupAnswer{a}` (`yes`, `no`, `again`, `skip`, `retry`, `ready`, `done`, `begin`, `later`, `cancel`, `close`), `setupLater`, `setupNever`, `setupReset`
  - `setDebug{on}`
- The status message's `setup` object has the offer, the aircraft's profile summary (with `included` when it's the package's), and, while the setup runs, its step, prompt and the answers that fit.
- Replies come back on `BetterReplay.Status`, `BetterReplay.Clips` and `BetterReplay.Reply`.

**Clip format.** The `.rpl` format is chunked and little-endian:

- `BRPL` + version, then `META` (event, UTC start, sample rate, stats, aircraft, airport), `CHAN` (channel keys and storage) and `SAMP` (frames).
- `VARS` (optional) lists which aircraft variable each input event and L:var channel recorded, since that depends on the aircraft and its profile.
- Unknown chunks and channels are skipped, and channels a clip doesn't have are left alone during playback. That leaves room for new channels and a future `LVAR` chunk without breaking old files.
- See [src/core/ClipFormat.h](src/core/ClipFormat.h).

## Event detection

Recording starts once the sim is running. Event detection arms 10 s after the flight loads, so spawning on a runway or in the air never creates a clip. Clips are written to disk as soon as each event finishes.

- **Takeoff:** starts 30 s before you roll onto the runway (the last runway you entered, so crossing another on the way out doesn't count). If you then wait on it for more than 30 s, the clip starts 60 s before the engines spool up. Ends 10 s after the flaps are fully up (lever and surfaces), or when back on the ground if that's sooner. If the flaps were already up at liftoff, it ends 2 minutes after liftoff, and if they're still out 5 minutes after liftoff (circuits, forgotten flaps), then.
  - Without a runway entry (spawned on the runway, or a strip the sim doesn't flag as one) it starts 5 s before the engines start spooling up: the last moment before liftoff that N1 (RPM on pistons) was at idle, the lowest it held steady for 5 s, within 3% of takeoff power. A 40% N1 stabilisation hold, a breakaway bump while taxiing or the engine start doesn't count as idle. Without engine readings either, it starts at the last moment you were below 10 kt on the ground.
- **Landing:** starts 3 minutes before the first touchdown. Ends at a complete stop (below 1 kt), 10 s after you leave the runway (crossing another one on the way starts the count again), or once airborne again for more than 15 s (a touch-and-go or go-around); shorter hops are bounces of the same landing. At most 170 s after touchdown, in case you never stop or leave the runway. Landings record touchdown vertical speed, peak G and bounce count.
- If the flight ends first (main menu, a new flight, slew, a teleport, a replay), a landing in progress and a takeoff past liftoff are saved up to that moment.

Recording pauses while the sim is paused, in slew, in the menus, during the sim's own replay, during BetterReplay playback, and while the [control setup](#control-setup) runs.

### Clip library and playback

- **Order:** newest first by when each clip ends (the time each row shows). So a "Save last 10 minutes" right after a takeoff lists above the takeoff clip, though it starts earlier.
- **Names:** each row is named after the aircraft and, for a takeoff or landing, the airport (*A350-900 | YMML*). The aircraft's name is its title without a note in brackets at the end (*A350-900 (Default Cabin)*). The airport is the one nearest the liftoff or touchdown, from the airports the sim lists around the aircraft, within 8 km; idents that aren't four letters (heliports and private strips, like *34CA*) count as 3 km further away, so a heliport by the runway doesn't win. With none near, and on clips from before airports were recorded, the row shows just the aircraft.
- **Aircraft match:** a clip replays only on the `aircraft.cfg` it was recorded with, down to the variant (an A350-900 clip doesn't play on the -900ULR or -1000). Clips from before the path was recorded go by the aircraft's title.
- **This aircraft / All aircraft:** the list shows the clips that replay on this aircraft, or with **All aircraft** every one, other aircraft's dimmed (their play button says which one to switch to). `clipsJson` marks each clip `playable` by the same check as Play (`Engine::recordedOnThisAircraft`), and the list is sent again when the aircraft's title or path changes, a variant included. Until the aircraft is identified (`aircraftKnown: false`), the panel lists every clip, without the choice.
- **Seek bar marks:** amber at the clip's liftoff or touchdown, green where the gear started coming down (`gearDownTime`, from the gear legs' positions like the replayed gear command): on a landing the last time before the touchdown, otherwise the first. No green mark if the gear never came down in the clip.
- **Stop** puts the aircraft back exactly where it was, with its velocities, resumes recording and returns to the main screen. On the ground it stays frozen until its gear is back down, 20 s at most; the main screen counts that down (*Unfreezing in N s*).
- **Retention:** only the newest 10 auto clips (takeoffs and landings) of each aircraft are retained; older ones are deleted when a new one is saved, and at startup. An aircraft here is the same as for the aircraft match: its `aircraft.cfg` down to the variant, or its title for clips without a path, so an A350-900 and -1000 keep 10 each. "Save last 10 min" clips (about 5.5 MB each) are never deleted automatically.

## Control setup

Aircraft differ in how their controls can be driven. Many 2024 aircraft keep their levers in their own input events or L:vars and overwrite the simvars playback would otherwise write. The setup finds out, once per aircraft, what actually works:

1. **The offer.** For an aircraft without a profile the panel always shows the setup. Until you're on a runway with the engines running it says so, with a checklist (parking brake set, on a runway, engines running) that ticks off as you get there; then it offers **Start setup**. Either way you can pick **Later** (until the next flight) or **Never for this aircraft**. While the setup is offered or running it fills the whole panel, with the steps across the top. **Set up** / **Redo** on the main screen's aircraft card starts it any time. The aircraft card shows its replay controls as *Configured* (green), *Partially configured* (yellow: some controls were skipped, didn't pass, or the gear is still to do) or *Not configured* (red).
2. **Each control, in turn:** spoilers, flaps and throttle on the ground (throttle needs the parking brake set), then the gear, still on the runway with the aircraft held just above it (below), or after takeoff where that doesn't work. Started in the air, the setup does only the gear. Controls the aircraft doesn't have are skipped.
   - **The gear without a takeoff.** Once the aircraft has stopped (*Come to a stop* otherwise), the setup snapshots it and puts it straight up from where it stands by its height above the ground there (`PLANE ALT ABOVE GROUND` on the runway, about as long as its gear) plus 30 ft, or by 50 ft where that isn't known; heading and attitude as they were, velocities zero, frozen with playback's freeze (`FREEZE_LATITUDE_LONGITUDE_SET`, `FREEZE_ALTITUDE_SET`, `FREEZE_ATTITUDE_SET`). Its position, attitude and velocities are written again every data frame meanwhile, in case the freeze doesn't hold. The panel says *Lifting the aircraft off the runway* (*No takeoff needed…*). Only once the sim shows it airborne up there (`SIM ON GROUND` false for half a second) does it ask "Raise the gear", and the gear step goes on as in flight. If the sim still has it on the ground after 5 s, or you raise the gear lever (where `GEAR HANDLE POSITION` shows it) and the gear doesn't move for 6 s (as long as playback waits for it), or the gear hasn't moved at all by the end of the usual wait for you (5 minutes), the aircraft goes back down and the step waits for a takeoff instead, with a note saying why (`control setup: can't set up the gear above the runway: …; it's set up after takeoff instead`).
   - **Back onto the runway.** However the gear step ends (done, skipped, not replayable, cancelled, **Finish later**, the aircraft changed), the gear has to be down first: each leg at least as far down as it was on the runway, and the gear handle down where its simvar showed it down then, for a second. The setup waits up to 30 s (*Waiting for the gear to come down*), then asks "Lower the gear" and waits for you, with **Cancel setup**, which puts the aircraft back as it is. A gear left up by a method that raised it and couldn't lower it can't be assumed lowerable by BetterReplay, so it doesn't try. Then the snapshot goes back (position, attitude, velocities) and the aircraft is unfrozen; the setup goes on once the sim shows it on the ground (half a second, 5 s at most). A flight loaded meanwhile, or the main menu, lets the aircraft go where the sim has it (unfrozen, not put back: the flight placed it), and so does the module stopping, which puts it back first. Look for `control setup: holding the aircraft N ft above where it stood`, `the aircraft counts as airborne above the runway`, `putting the aircraft back where it stood on the runway (gear at 1.00)` and `put the aircraft back where it stood, lat … ; unfreezing`.
   - **You move it,** one instruction at a time: "Deploy the spoilers", then "Retract the spoilers" (back past where you started them counts too, and isn't a movement of its own: the A380's lever armed, its handle at 0.06, retracted to 0; the setup, and each replay's check, go only by how far out they are); for the throttle "Move the throttle to about halfway and hold it", "Now to full and hold it", "Back to idle", "Wait for the engines to spool down". Each gets a green tick once it's done. A hold shows a ring that fills while the throttle is held still (the throttle's input events, the cockpit lever, moving less than 2% a second for 2 s, once they've moved with the throttle; on an aircraft whose input events don't, its simvar the same way; on a lever with detents, the detent nearest halfway will do). On the iniBuilds A380 the simvar, a thrust demand, held at halfway but never at full: a minute at TOGA and no tick. Not the simvar once the input events have moved: the A380's first hold ticked by them while its simvar, a thrust demand, was still catching up (27% of its 69% at halfway), and the simvar then held there and ticked "full" with the lever still at halfway. The log says which one held (`control setup: throttle held, by its input events at Y (hold 1 of 2); the lever simvar at X%, …`, or `throttle held at X% (hold 1 of 2; its input events, which haven't moved, at Y)`), and every 15 s without a hold what both are doing (`control setup: no throttle hold yet after 15 s (hold 2 of 2): …`), and dots beside *Your turn* show how far through the step's instructions you are. Meanwhile every input event and L:var the aircraft has is watched, to find the ones that moved with the control, whatever they're called, and so is every key event that fires (a cockpit click, one of your bindings), since an aircraft's own events show in no variable; BetterReplay's own aren't counted. When you're done the log lists them, a line per kind: how often it fired with the movement and before it, when (from the moment the control moved) and with what parameters (`control setup: N key event(s) of M kind(s) while you moved the gear …`). One run on the PMDG 777 or DC-6 shows what its cockpit lever and your bindings send, if anything: that hasn't been seen in the sim yet. For the gear, flaps and spoilers it then asks for the first instruction once more ("Raise the gear"; *Once more, and leave it there*) and waits until the control is there and still, for the way back on its own (below).
   - **It replays your movement**, with each candidate method in turn: the aircraft's own input event preset (the cockpit's path), the key events it saw fire with your movement, the legacy key events (`FLAPS_SET`, `SPOILERS_SET`…; `FLAPS_SET` takes the handle index over `FLAPS NUM HANDLE POSITIONS`, which is the highest index: sent over one less, the A380's notch 2 of 4 went to 3), then what hardware bindings send for aircraft that ignore those (the PMDG 737): `FLAPS_INCR`/`FLAPS_DECR` a notch at a time toward the recorded handle position (going by where the notches sent left the lever, kept across replays, and by the aircraft's handle again only once it has held still for 30 s since it last moved and the last notch: the PMDG 777's handle follows its flaps, a detent every ten seconds or so, and going by it sent extra notches that ran them to 25; each notch is logged), `AXIS_FLAPS_SET`, `AXIS_SPOILER_SET`; then the simvars, then the L:vars it found. Hands off the controls meanwhile. An L:var it found may only animate one panel (the PMDG's `NGXLeftInbdTrailFlaps` moved one flap section), so after trying one the setup puts it back as it was. For the gear, a variable that took 2 s or more to travel, or most of the time the legs took, follows them: it's a leg's animation (the PMDG 777's `7X7XleftMLGExt` swung only the left main gear), not the lever, so it isn't tried. The log gives each candidate's travel time. A replay leaves out the middle of a long stretch where the control sat still between its moves (the 777's gear up for 20 s of a 48 s movement, waiting for *Lower the gear*): it keeps as long as a method gets to start moving the control and 1.5 s more after it stopped, and your lag and a second more before it moved again (`control setup: replays leave out 18.2 s where the gear sat still: 30.3 s of your 48.5 s`). Not for the throttle, whose holds are part of its check. Before each replay the control goes back to where your movement started it (up to 30 s; the last method may have left it elsewhere), and only movement from there counts. A method that hasn't started it back there within as long as it gets to start moving it (below) isn't replayed, as nothing the check counts can come of it (`control setup: … didn't bring the gear back to where you started it (it didn't move); not replaying it`): with the 777's gear left up by the way back, its lever event waited 30 s and then replayed all 48 s of the movement. Only movement from there counts: on the 777 a method that only lowers the gear otherwise passed after one that only raised it. And only the way you moved it (the flaps and spoilers out, the throttle up, the gear up): from 1+F the A320neo V2's `HANDLING_FLAPS_SET` put its flaps up to 0 whatever it was sent, and counted as moving them 336% as far as your notch 2 (`… moved the flaps 0% as far as you did; it went the other way, past where you started it`). Your own movement counts only that way too. For the gear the log then says where it went after each command (`gear up at 0.5 s: the gear went from 1.00 to 0.00`).
   - **The key events seen** (two at most, not for the throttle, whose key-event method sends the axis anyway) are matched to the control's value: the spoiler handle, the flap handle index, or the gear command from the legs. One that also fired twice or more before the movement fires steadily (an axis, a gauge) and is left out, and so are the legacy events tried anyway. An event whose parameter followed the value is a *position* (a lever's position, an axis; on the gear two values will do, elsewhere it takes three): the replay sends the parameters it fired with, when they fired, and playback turns the clip's value into the parameter the same way (`#70001`, or `#70010@-16383` with an offset added). Otherwise each of its parameters is a click: a *toggle* if the control moved one way within 5 s of one and back after the next (`#66587(29501)`, `ROTOR_BRAKE` with a PMDG cockpit code), or a *step* if it always moved the same way, paired with one that moved it back (`#69940(536870912)/#69940(-2147483648)`, a lever's left and right click). Those replay like you clicking: one toward the clip's value, the next once the aircraft shows it (up to 6 s for the gear, whose legs start late; a second elsewhere). The aircraft's own events (69632 and up) are sent through SimConnect, mapped by number, sim key events directly. After them, before the legacy key events, come the ways an aircraft's SDK gives its own gear lever event, those not seen already, for when the lever's event didn't show: the aircraft's entry in `kOwnGearLevers` names the event and the SDK's mouse flags, and the setup tries the event's position and a left click on the lever (the button, then its release, on the same event: `#69927(536870912,131072)`, sent as a toggle). On the PMDG 777 that's `#69927`, its `EVT_GEAR_LEVER`, sent through SimConnect. Which of them works which way isn't in the table: the setup finds that by trying (below). Its cockpit lever sends no key event the setup can see. Of the gear variables left, the one that changed first is tried first: the lever leads (the 777's `switch_295_a`), sound and airflow flags follow the legs.
   - **It checks the result automatically:** did the spoilers, flap surfaces, gear or N1 (RPM on pistons) move at least 60% as far as when you did it, and come back? The flap surfaces are the trailing edge and the slats together, and so is what ticks *Wait for the flaps to extend*: the A220's notch 1 puts out only its slats (21° of 27°), and going by the trailing edge alone that never ticked, so you went on to notch 2 (`you moved the flaps … (handle moved 1, outcome 0.78; …)`). Methods that fail move straight on to the next one. One that passes but went less than 90% as far waits: the others are tried first, and one of them that goes further is asked about instead (`control setup: … moved the spoilers only 76% as far as you did; trying the other method(s) first`). If none does, or you say no to those that do, the one that went furthest is replayed once more and asked about, with a note saying how far it went (`control setup: back to …, which went furthest (76% as far as you did); replaying it once more to ask`). The last method is asked about at once if it went furthest. The panel marks one waiting like that *Method N only went part way*. The A380's `SPOILERS_SET` went 76% as far: the lever half way, the spoilers half out. **Watch again** and that last replay are always asked about, and a method that went one way and another brought back is asked about as before.
     - **Spoiler calibration.** A spoiler key event that takes a position (`SPOILERS_SET`, `AXIS_SPOILER_SET`) and went part way (moved them and brought them back, but less than 90% as far) is first stepped through its range: none to full in 20 steps, each held until the handle has been still 0.3 s (3 s at most), then back. The panel shows *Testing the spoilers: N%*. If the steps took the handle at least 90% as far as you did, and the value that puts it where you did isn't the value itself, the replay is run again through that table (the event's value that put the handle where the clip has it) and checked as usual; else the replay before it stands and the part-way rule above goes on. Each event is stepped once a step. The A380 puts its lever half way for the handle's 0.52 at full, and both events went 76%: `control setup: SPOILERS_SET stepped from none to full put the handle from 0 to 0.52 (yours went to 0.52)`, `SPOILERS_SET calibrated (21 points): your 0.52 is SPOILERS_SET at 1; replaying it through that`. The table goes into the profile under the spoilers' `"lever"` (`var` the event, `forward` its [value, handle] pairs), and replays send that event through it (`controls: the spoilers through SPOILERS_SET's calibration (21 point(s))`). **Ground spoilers** take the handle further than that: armed, the A380's took it from 0 to 1 within a second of touchdown, the surfaces all the way out, and a replay through the lever put the lever at full and the spoilers half out. So where a clip's handle went more than 0.05 beyond the calibration's top from a moment on the ground, the replay arms the spoilers (`SPOILERS_ARM_SET 1`) 30 s ahead, with the clip's lever retracted, and leaves the handle to the aircraft until the clip's come back within the lever's reach; then it disarms them and the lever follows the clip again. If `SPOILERS ARMED` still reads 0 a second after arming, it sends `SPOILERS_ARM_ON`; if the aircraft's handle hasn't gone beyond the lever's reach 3 s into the stretch (or into a seek there), the lever as the clip has it, as before. Stop, or another clip, puts the arming back as it was before the replay. Look for `controls: ground spoilers in N stretch(es) of the clip …`, `spoilers armed (SPOILERS_ARM_SET 1) at …`, then `the aircraft's ground spoilers came out at … (handle …)` or `no ground spoilers 3 s into the clip's (…); the lever as the clip has it from here`, and at the end `ground spoilers: armed N time(s); the aircraft's came out N time(s), the lever instead N time(s)`. On the A380 the arming took at once, its ground spoilers came out at touchdown, all the way, and went in where the clip's did. One that hasn't moved the control at all a while after your movement had moved it isn't replayed to the end: the control is held where your movement ended until it's still, and the check fails it (`control setup: no movement of the flaps 7.0 s after yours; not replaying the rest`). That while is as on the way back: 3 s (for the gear as long as playback waits for it, 360 frames at the frame rate the setup sees, 6 s at least: 9.7 s at the A380's 37 fps), plus as long as the aircraft took to show your movement on what the check reads, from its first sign (`control setup: the outcome moved 4.0 s after the first sign of your movement; a method gets 7.0 s to start moving it`). The PMDG 777's flaps start about 3 s after the command, and take another second to move as far as counts.
     - **An input event's preset in another range.** A preset can take another range than its input event reads: the FSS E-Jets' `EVT_LEVER_THROTTLE_B` reads the lever 0..1, but its `_SET` is what `THROTTLE_AXIS_SET_EX1` is bound to and takes the axis's -1..1 (`p0 0.5 * 0.5 +`). Sent the 0 it read at idle, the levers went to half and stayed there, so every method after it started there, never saw the engines at idle, and went 0%. And on the E190 the `_SET` doesn't take what it's sent at all: in the sim it read 0.5 for 0, 0.25, 0.5 and 1, as if sent 0 every time (its preset's parameter is RPN, `RPN="True"`, unlike the cockpit levers' presets; a double passed to `fsVarsBVarCall` doesn't seem to reach it), so its first call put the levers at half, where they stayed: that was the 53% the first replays reached. Written directly (`SimConnect_SetInputEvent`, the "value written directly" method) it did take the value: 0.504 read 0.752, 1 read 1, 0 read 0.5. So before the throttle's replay with an input event (its `_SET` or its value written directly), the setup probes it (*Listen to the engines*, about a second): sent where your movement starts, then a quarter of the way to where you took it (well short of a detent like CL or TOGA), each held until what the event reads (`fsVarsBVarGet`, the same read as the scan) has held still for 6 frames (a second at most: the value written directly lands a frame or two later). `control setup: trying … (method 1 of N): first what it reads for what it's sent`, then `EVT_LEVER_THROTTLE_B read 0; sent 0 it read 0.5, sent 0.25 it read 0.5`. Reading the same for both, the method isn't replayed, and the same event's value written directly goes next (`… reads the same whatever it's sent: not replaying it; trying its value written directly next`). Reading a straight line that isn't what it was sent, the same method with that undone goes next instead, and this one isn't replayed (`the input event reads 0.5 x what it's sent + 0.5, not what it's sent: trying input event EVT_LEVER_THROTTLE_B (value written directly, sent 2 x value - 1) instead`). Reading nothing (`it can't be read back; its replay will show`), or as meant, it's replayed. A method tried again after you brought the throttle back to idle (below) isn't probed again: the probe may be what left it off idle. Where the probe can't tell, the replay shows it: while an input event replays, the setup reads the event back each frame and pairs what it was sent with what it read once that has held for 6 frames. If the pairs spread over a quarter of what the method sends, lie on a straight line (within 3% of what they read: a clamp isn't one), and that line reads more than 3% off what the replay meant, the same event is tried next with that undone, unless this one went all the way anyway (`… the input event read 0.5 x what its _SET was sent + 0.5, not what the replay meant: trying … next`); its first frame brings the control back to where you started it. Either way the log has what it read (`what EVT_LEVER_THROTTLE_B_SET was sent and what the event read: sent 0 read 0.5, …`, and why it didn't convert), and a throttle replay of a variable logs every 2 s what it sent, what that read, the lever simvar and N1 (`control setup:   4 s: sent 0.5, EVT_LEVER_THROTTLE_B reads 0.75; …`). The profile keeps the conversion as the method's `scale` and `offset` (sent `value * scale + offset`), and playback sends the same.
     - **The throttle back to idle.** A throttle method can leave the engines off idle where the next can't bring them back: on the E190 the first left the levers at half, and every method after it waited 30 s for idle, replayed anyway and went 0%, though nothing had tested it. Now, where the throttle isn't back where you started it 30 s into a method's wait, the panel says *Bring the throttle back to idle* (move it up a little and back, so your throttle's own input takes the levers back), holding the brakes meanwhile, and once it's been there 1.5 s that method starts again from there (`the throttle didn't go back to where you started it within 30 s with …; asking you to bring it back to idle`, then `the throttle is back where you started it after N s; trying … again from there`). Once per method: one that takes it away again itself replays anyway, as before.
   - **Each way on its own** (the gear, flaps and spoilers). How a control comes back can depend on how it got there. On the PMDG 777 its lever event's position 0 raised the gear but 1 didn't lower it; `GEAR_SET`/`GEAR_DOWN` lowered it after the event had raised it, but after you had raised it only a left click on the lever did. A replay of your whole movement starts with the control where you left it, at rest, so it never meets that. So once you've moved the control away again, the way back is replayed from there with each method in turn until one brings it back (not the simvars: written, they move what the check reads, and you aren't asked about these). Back where your movement started it and still, it counts. Past there, the other way from your movement (the flaps up to 0 from 1+F), it doesn't (`(it went past where you started it)`), and the others aren't tried from there, as bringing it back from the other side isn't the way back: on the A320neo V2 `FLAPS_SET`, tried after `HANDLING_FLAPS_SET` had put the flaps up to 0 from notch 2, counted as bringing them back by lowering them to 1+F. The way back is then only tried from where the replays leave it (`control setup: the flaps went past where you started it: the way back is only tried from where the replays leave it`). Not on its way back within as long as playback waits for it (the gear's 360 frames, as above) or 3 s otherwise, plus as long as the aircraft took to show your movement (below), it doesn't. On its way back means moved as far as counts as moving (0.05 of the gear's travel), not as near as counts as back: the A380's gear legs start down about 6 s after `GEAR_DOWN` (its doors first), were 0.12 down when the wait ran out, and the light's L:var tried next got the credit. Nor does a pause count as stopping short while the gear's legs are split, some where your movement started them and others not (of the legs that moved in it): the A380 lowers its nose leg all the way, then its main legs about 10 s later, and their mean sat at 0.34 between. The same goes for the settling after each replay and for your raising it once more. A click or a step (a toggle, an aircraft's own event's steps) gets as long again as playback waits before sending it once more (360 frames for the gear, 60 otherwise, in seconds at the frame rate the setup sees): after the 777's lever event, its first click on the lever did nothing and the second lowered the gear, about 10 s in at 37 fps. Given less, the 777's flaps came back while the method after the one that did it was being tried, and that one got the credit. Then the whole movement is replayed with each method as above. One that moves the control away but doesn't bring it back gets the way back replayed from where it left it (unless that's past where your movement started it), with the method that brought it back from where you left it first and then the others; if one does, that pair is put to you. The log has a line for each (`control setup: … brought the gear back from where you left it`, `… didn't bring the gear back from where the replay left it (it didn't move)`) and, for the gear, where it went after each command.
   - **Ways for each direction.** Where one method doesn't do it all, the profile keeps for each direction the ways to try, in order: out with the method you confirmed; back with it, or the one that brought it back after it, then the one that brought it back from where you left it. On the 777: up `#69927`; down the gear key events, then the click. In `aircraft.json` they're lists of `{method, var, scale}` (and `offset`, where an input event's preset needs one) under each control: `"down"` and `"up"` for the gear, `"extend"` and `"retract"` for the flaps and spoilers. A control without them has its one method both ways, as in profiles from before; the 777's `#69927+keys` from the builds just before is read as these lists.
   - **It asks you:** "Did the engines spool up and back down?" **Yes** keeps that method, **No** tries the next, **Watch again** replays it once more, **Skip** leaves the control as it is without a profile (on a later run, a control that was already set up keeps its earlier setup).
   - If nothing works, the control is marked *not replayable*, and replays leave it to the aircraft instead of fighting it.
   - **Spoilers that don't come up on the ground** are taken as *automatic* (`automatic` in `aircraft.json`), and replays leave them to the aircraft, as for *not replayable*, but the aircraft card counts them as set up. On the FSS E-Jets neither the spoilers nor their handle simvar move on the ground whatever the lever does, and in the air the setup found no way to move what the aircraft draws (its own spoiler variables, from its own lever); its ground spoilers come up by themselves on landing. While the spoiler step waits for your movement, their lever moving without them says so: an input event named like the spoilers (`SPOILER`, `SPEED_BRAKE`…), or an L:var named like their lever (that and `LEVER` or `HANDLE`: not an indication), not an arming flag (`ARM`), that held still for the step's first second (not something settling as it starts), then stayed a fifth of its range (1, or 100 where it reads more) from where it was for 1.5 s, with neither the handle simvar nor the spoilers moving: `control setup: input event EVT_LEVER_SPOILER_2, L:var FSS_EXX_SPOILER_BV_LEVER moved, but neither the spoilers' handle simvar (0) nor the spoilers (0) did: they don't come up on the ground here; taken as automatic, left to the aircraft in replays`. The setup goes on with the next step and says so (*The spoilers don't come up on the ground on this aircraft, so they're taken as automatic…*). On aircraft whose spoilers come up on the ground, their handle simvar or the spoilers move first, and the step is as it was.
   - **The brakes are held** while the engines run up on the ground (your throttle movement, its replays, *Moving the throttle*): `BRAKES` every frame, as holding the `.` key does, on top of the parking brake. The A220's parking brake alone didn't hold it at full thrust; it rolled at 7.5 kt by the end of the pilot's movement, and again at 3 kt in a replay. Not while it asks, and the toe brakes let go by themselves once it stops. Where holding them let go of the parking brake (as the pedals do on a real Boeing), the setup sets it again (`PARKING_BRAKE_SET 1`) once it stops holding them. A throttle replay waits (up to 30 s) for the aircraft to stop before it starts: the A220's first replay began at 7.5 kt and stopped at once. Look for `control setup: holding the brakes (BRAKES, as the "." key) while the engines run up, as well as the parking brake` and, where it let go, `the parking brake was let go while the brakes were held; setting it again`.
   - **Engines still spooling down** when the throttle step starts (from the taxi, or with spoilers and flaps skipped straight away) settle before your movement: until the throttle moves, where the engines started is the lowest they've been, and engines below where they started count as spooled down, as the spoilers count back past where they started. The A220 started its step at 29% N1 on its way to its 21% idle; that fall counted as your movement (`the throttle started moving (0 -> 0, outcome 29.1 -> 27.1)`), and *Wait for the engines to spool down* waited for 29% at idle.
   - If the aircraft starts to roll anyway during the throttle replay, it stops and goes back to idle, and the panel says *Stopped early: the aircraft started to move. If the parking brake is set, hold the brakes as well, then Watch again.* (The sweep's says *Try again*.)
   - **The throttle lever,** only where it's needed. On some aircraft the lever simvar isn't the lever: on the A320neo V2 it's the autothrust's thrust demand, about 85 at TOGA and creeping with speed while the lever sits in its detent. That's what the throttle's two holds are for: if the simvar kept moving while a lever-like variable held still (your hand was still), and the throttle replays with the key events, the step goes on. If the holds didn't tell (say the simvar held still but read short of 100% at full, like a thrust demand that settles at once), it asks "Do the levers stay put under autothrust?". Aircraft whose simvar is the lever skip the lever calibration (but not the reverse test below). In tests it also ran on the CJ4 (its FADEC sets the simvar) and the PMDG 737 (the simvar trailed its lever by a few percent), and replays from their levers' own variables work well.
     - **The lever's own variable** comes from the same holds: the L:var that moved with the throttle and held still at idle, halfway and full for the longest (the thrust demand keeps creeping; flags and detent indexes take too few values). So there's no second pass of the throttle. Only if no variable did, the setup asks for the holds once more: "Move the throttle to about halfway and hold it", "Now to full and hold it", "Back to idle".
     - **"Moving the throttle":** straight after, the setup steps the throttle axis (`THROTTLEn_AXIS_SET_EX1`) from the bottom to full in 2.5% steps and notes where the lever went (the lever's variable may run either way: the PMDG 737's goes from 500 at idle down to 75 at full). Then, with reversers that aren't on the axis, it finds how this aircraft takes reverse thrust, checking that the reversers actually deployed (their nozzles out, or the lever simvar below idle; the reverse flag alone doesn't count). First the reverse events (`SET_THROTTLEn_REVERSE_THRUST_ON`), stepping the reverse amount on the axis. If half the axis hasn't deployed anything, it stops there (the PMDG moves its forward levers instead) and tries "toggle reverse" (`THROTTLE_REVERSE_THRUST_TOGGLE`, the A350's way, which ignores the reverse events): once the throttle simvar is back at idle it toggles, steps the amount on the axis until the reversers are out and the simvar has gone 5% further into reverse than at reverse idle, then back to idle, toggles back, and checks with a little forward thrust (15% of the axis) that the aircraft is out of reverse. Still in reverse, it toggles again (twice at most, then it stops and asks you to toggle it out yourself): the toggle is remembered by the aircraft, so it's never left on. If the toggle didn't work either, it tries "decrease throttle" held at idle (`THROTTLE_DECR` every frame, like holding F2), then lets go and waits for the reversers to stow. Then it puts the throttle back to idle. The engines spool up against the parking brake for 20 to 40 seconds; if the aircraft starts to roll it stops.
     - The lever's L:var, that table and how reverse works go into the profile. Clips then record the lever (`lv_thr_N`), and replays turn it back into the axis value that put it there: the middle of a detent when it was in one, so it lands in the detent. Clips recorded before this replay from the simvar as before, and so does any stretch of a clip longer than a second without the lever's value (recorded before the setup found the variable, or before the aircraft had it).
     - **Autothrust in replays.** On these aircraft the levers stay in their detent under autothrust while the thrust demand (the lever simvar) goes where the autothrust puts it; replayed from the lever, the engines would give the detent's own thrust, climb power down a whole approach. So when a clip loads, the replay finds where its autothrust was in control: the lever held still for more than 10 s, above idle, while the demand still moved more than 8% after the first 10 s (more than it does catching up with a lever move, or creeping with speed in FLX on a takeoff roll). That whole hold counts, and the lever coming back from it towards idle (3 s at most, the retard). There the throttle axis follows the clip's thrust demand: a first guess from the demand itself, corrected by how far the aircraft's own demand is off the clip's (`ThrustFollower`), and never further forward than the clip's lever. Its corrections go to the aircraft only when they're 3% of the axis or more, or 0.5% that has lasted half a second: sent at every 0.15% change, the first test replays sent about 20 throttle events a second and the engine sound was distorted, though N1 was within 1.1% of the clip. The engines then spool as they did in the clip, but the cockpit levers sit where that thrust needs them (just above idle on an approach), not in CL. The log says `controls: autothrust in N stretch(es) of the clip (… s)` at the start of the replay.
     - **The FSS E-Jets' autothrottle in replays.** Their throttle replays through the input event `EVT_LEVER_THROTTLE_B`, which reads the pilot's throttle, while their autothrottle moves the levers themselves (the lever simvar, 100 x the input where the two agree, 93.9% at the top). In a takeoff the A/T flew, the levers sat at 87% (N1 90.5) with the pilot's throttle at 0.69; replayed through the input with the A/T off, the levers went to 69% and N1 was 8.7% off the clip on average. So when a clip loads, the replay finds where its levers were more than 8% of their travel away from the input and held there, not closing on it by 1% a second (as the lever following the pilot's throttle does: it takes 6 s or so from idle) for 2 s somewhere (`autothrottleLeverStretches`); a stretch runs from where the levers left the input to where they came back within 8%, or the reversers came out. There the levers' position goes through the input instead. On that takeoff, one stretch from 16.6 s to the end: where the A/T took the levers past the pilot's 0.69. Only input events listed in `kLeverInputs` (ControlDriver.cpp) do this: every other aircraft's throttle replays as before. The log says `controls: the clip's autothrottle held the thrust levers away from the pilot's throttle in N stretch(es) …` at the start, and `controls: N engine frame(s) sent the clip's thrust levers, …` at the end.
     - **The FSS E-Jets' reverse in replays.** Their input reads the pilot's throttle from idle up and takes no reverse, and the setup's reverse test only runs on key-event throttles, so a landing's reverse never replayed (N1 41% off the clip where its reversers were out). In the clip the lever simvar went to -40% with the nozzles at 79% while the input stayed at 0; the pilot's throttle moving a little from idle took the levers out again. The pilot's "decrease throttle" binding (a joystick button held) goes to their own input event `EVT_LEVER_THROTTLE_DEC` (their `Throttle.xml` intercepts `THROTTLE_DECR`), which takes their lever variable (`FSS_EXX_LEVER_THROTTLE_B_MOUSE_INP`, 0.3 at idle, 0.17 to 0 reverse) 0.01 lower each time. The sim's `THROTTLE_DECR` sent from the module doesn't reach it: a replay holding that for the whole reverse (829 frames) left the levers at idle. So each entry in `kLeverInputs` names the aircraft's decrease and cut input events and the lever variable, and replays reverse as "hold" without the setup (`LeverReverseHold`): the decrease's `_SET` preset every frame while the clip's lever simvar is below idle (full reverse; the nozzles stow after the levers), the input not sent meanwhile (a new value from it takes the levers out of reverse). If the lever variable hasn't gone down 10 frames in, it's written instead, 0.01 lower a frame. When the clip's levers come out, the variable goes back to idle and the input as the clip has it; levers still in reverse 30 frames on get the aircraft's cut (`EVT_LEVER_THROTTLE_B_CUT`), and so does a replay that ends in reverse. Look for `controls: holding EVT_LEVER_THROTTLE_DEC …`, `the aircraft's levers are in reverse after N frame(s) …`, `60 frames into the hold: …` and `the levers are out of reverse N frame(s) after letting go`. In the sim, on a landing with 23 s of full reverse: the preset took the variable from 0.3 to 0 within 60 frames, the levers showed reverse after 71 (they swing over about 2 s, as in the clip), and were out 3 frames after letting go. N1 was 3.9% off the clip where its reversers were out (from 41%), 1.5% over the whole replay (from 4.7%). A replay stopped in reverse hasn't been tried.
     - **Reverse thrust, on any aircraft with reversers** whose throttle replays with the key events: if it needs no lever calibration (its simvar is the lever, or you said its levers move with the thrust, like the PMDG 737), *Moving the throttle* runs the reverse test alone, up to half a minute.
     - **Reverse in replays** follows what the clip's reversers did, however you commanded them. On an aircraft that takes "decrease throttle", the replay holds `THROTTLE_DECR` while the clip's reversers are out and lets go after: that's all or nothing, full reverse while held. On one that takes the reverse events, the replay sends them when the clip's reverse flag does, and puts the reverser in itself when the clip reversed without it ("decrease throttle" held, or an aircraft that never sets it). The aircraft counts as in reverse once its reversers are out, flag or not: the A220 never sets it, and waiting for it a landing's full reverse replayed at reverse idle (N1 18.7% off the clip where its reversers were out, 58.7% at most). The amount comes from the reverse table, or the lever simvar where that's more, until the clip's lever variable has shown reverse; from then until the reversers go in, from the lever's alone. With "decrease throttle" held the lever variable stays at idle and only the simvar shows the amount, but the A220's simvar sits at its lower limit (-20%) all through reverse, reverse idle too, and going by it every reverse would be full. On one that takes "toggle reverse" the replay toggles it when the clip's reversers come out, with the levers at idle and held there until the toggle has settled, then sets the clip's reverse amount (its throttle simvar over `THROTTLE LOWER LIMIT`), so idle reverse replays as idle reverse; when the clip's reversers go in it puts the levers back to idle and toggles out once the reverse amount is gone. Neither the A350 nor the PMDG sets the reverse flag, so "in reverse" means the reversers deployed, in the clip and on the aircraft. The A350 doesn't show reverse at reverse idle (its nozzles and simvar only show the amount), so the replay keeps track of the toggle itself, corrected by what the aircraft shows: a first small amount (20%) goes until the aircraft shows reverse; forward thrust from it means the toggle didn't take, and so does reverse where the clip has forward thrust; then it toggles again (three tries each time). Neither for 30 frames, the throttle simvar not rising, means the toggle took, and the clip's amount follows: the A380 shows nothing at 20%, and a replay stayed there through the clip's full reverse, the reversing engines' N1 at idle (3.7% off the clip on average, against 0.7% for the outer engines; taken as in reverse after 30 frames, 3.3% where the clip's reversers were out) (`controls: the aircraft shows reverse; …`, or `controls: no forward thrust from the first reverse amount, nor reverse shown: taken as in reverse; …`). At the end of a replay, a reversing engine's N1 line also says how far off it was where the clip's reversers were out. Its throttle simvar lags the lever by seconds, so while it's still heading back to idle neither counts. Seeking out of reverse toggles out the same way, and at the end of a replay the throttle is held until reverse is toggled out (10 s at most) before it's let go. Profiles made before this test leave reverse as before: redo the throttle step to get it.
3. **Replays** then drive each set-up control with its method, through the same code the setup tested. Clips recorded before the setup (or from different variables) fall back to the defaults for that control, and the log says so.
   - **Ahead of the clip.** The setup also notes how much later than in your movement the method it kept moved the gear, flaps or spoilers in its replay (`control setup: … moved the flaps 3.1 s later than you did`). Half a second or more (10 s at most) is kept in the profile (`"leadSec"`), and replays drive that control that far ahead of the clip (times the playback speed): `control setup: replays drive the flaps 3.1 s ahead of the clip`, then in replays `playback: the flaps driven 3.1 s ahead of the clip`. On the PMDG 777 the flap handle follows the flaps, so a clip has it moving when they started, about 3 s after the lever; a notch sent then moved them about 3 s later again, and the flaps went up 5 to 10 s after they had in the flight. Profiles from before have no lead: redo the step to get one.
   - **The autothrottle off.** A replay of a clip with throttle data triggers the sim's `AUTO_THROTTLE_DISCONNECT` key event (what an "autothrottle disconnect" binding sends) twice, half a second apart, after each jump (Play or a seek): engaged, the autothrottle drove the levers against the replay's (the PMDG 777 held 106% N1, and most of the takeoff roll stayed near 90%). Not before the jump: frozen in the air at a takeoff clip's 0 kt, the 777's engaged itself again. The second press clears the disconnect warning; with the autothrottle off neither does anything. Nothing aircraft-specific: an aircraft that doesn't take the sim's event keeps its autothrottle. It stays off after the replay. Look for `playback: sent AUTO_THROTTLE_DISCONNECT (twice)`. After the second press the throttle goes out again: the levers stay where the autothrottle left them, and the replay only sends them when the clip's move. The one exception is aircraft that show their own autothrottle in an L:var: the FSS E-Jets' `FSS_EXX_FGC_LT_AT`, listed under their profile key in `kAutothrottleLights` (AircraftProfile.cpp, `autothrottleLight`), so the E170, E175 and E195 too. It goes by the key, not by whether the L:var is there: an L:var stays registered for the rest of the sim session once an aircraft has made it, and an A320neo V2 loaded after an E190 took the E190's light for its own, and so went without its presses. Their `AUTO_THROTTLE_DISCONNECT` goes to the button on the thrust levers, which toggles it: two presses left it on, holding climb thrust through a takeoff replay started in a climb (`the engines have settled …, short of the clip (N1 90.3/26.3 …)`). There the presses go by the light: one while it reads on, read again 0.7 s later, two at most (`playback: the autothrottle's on/off is L:FSS_EXX_FGC_LT_AT here …`, then `the autothrottle is off (L:… reads off after 1 AUTO_THROTTLE_DISCONNECT press(es)) …`, or a warning if it still reads on; on an E-Jet that hasn't made the L:var, `playback: no L:FSS_EXX_FGC_LT_AT … on this aircraft yet`, and the two presses).
     - **And for the rest of the replay:** with its A/T arm switches on, the 777's engaged itself again at the clip's acceleration altitude and drove the levers from there. So the replay watches the thrust levers (`LeverWatch`): where they've been more than 3% of the axis off where it put them for half a second (back for less than a second doesn't count: a lever the replay sends may jump back for a moment before the autothrottle has it again), it presses the disconnect twice again and sends the throttle after it; 3 s apart at the soonest, 10 times a replay at most. A press it didn't need (the levers just slow to follow a fast move) does nothing with the autothrottle off. Nothing in it is aircraft-specific: it goes by the levers alone. The levers are read from the lever's own variable through its calibration where the throttle replays from that, else from the lever simvar (not on an axis with its own reverse zone), and not in or around reverse. Look for `playback: the thrust levers have been up to N% of their travel off where the replay put them …`, then `… are back where the replay puts them, N s after the disconnect`. On the 777 that works, but not smoothly: the half second the levers have to be off first, and the disconnect after it, make its move from MCT to CLB uneven where the clip's was smooth. A possible fix is to disarm the A/T for the whole replay.
   - **Ways for each direction** are all got ready, and each command (the clip's value leaving the aircraft's, one way) starts with the first of that direction's list. If the control hasn't moved that way after the wait (360 frames for the gear, 6 s at 60 fps; 60 frames otherwise), the next one takes over, round the list (`WayPicker`); one that has moved it stays for the rest of that command. The control has moved when its value has (the gear's command from its legs, the flap handle index, the spoiler handle) or what it moves has gone that way (the legs, the flap or spoiler surfaces). The log says which way it went with (`controls: the gear went down with … (not the first way: first from now on)`). A way that worked where the one before it didn't goes to the front of its list, in the replay and in `aircraft.json` (`control profile: the gear down with … first from now on`), so the app keeps learning in use: on the 777 the click goes first after it has lowered a gear you raised, the key events after they've lowered one a replay raised. Ways the clip can't feed (recorded from another variable) are left out for that replay. After **Stop**, a gear with ways for each direction is driven back to where it was until it's there (50 s at most), so the next way can take over there too.

**Recording stops while the setup runs,** from **Start setup** until its results screen, and that includes the gear step above the runway, putting the aircraft back, and waiting for a takeoff where the gear is done after it. So its spool-ups and gear cycles never end up in a clip. A takeoff or landing in progress when it starts is saved up to that moment. When the setup finishes, or you pick **Finish later**, recording starts again from an empty buffer, and detection arms 10 s later, as after a teleport. On the flight you set up an aircraft, the takeoff isn't saved but the landing is, with the new profile. The results screen says *Recording starts again now*, and the log `recording starts afresh after the control setup`.

If you skip the gear step or quit before it, the panel offers just the gear once you're airborne again. Profiles are kept per aircraft in `aircraft.json` in the work folder, shared by its variants: the key is the aircraft's folder under `SimObjects` (from its `aircraft.cfg` path), so its presets share it, without the model's variant number (a dash and 3 or 4 digits after the model's own digits). So the PMDG 737-600, -700, -800 and -900 share one profile, and so do the A350-900, -900ULR and -1000. A few families the dash rule doesn't join are listed in `kFamilyAliases` (AircraftProfile.cpp): the FSS E195 shares the E190's (the same `fss.wasm`, behaviour files and flap detents), and so do their E170 and E175 (taken to be the same, in folders named like the E190's; not seen yet) and any E-Jet livery folder of its own (`e190-…`; their liveries report the base folder). The PMDG 777F shares the other 777s'. Clips don't: they replay only on the `aircraft.cfg` they were recorded with. Profiles kept per variant before are moved over at startup (where variants had one each, the newest is kept).

### Included profiles

The package can include profiles of its own in `profiles\aircraft.json`, in the same format as the work folder's. In the repo they're one file per aircraft in `profiles\`, exported from a work folder with `tools\export-profiles.mjs` and combined by `build.ps1` (see [Tests and tools](#tests-and-tools)). An aircraft with a profile in the work folder's `aircraft.json` always uses that one. Without one, it uses the included profile, and the aircraft card says *Included* instead of *Configured* (the status message's `setup.included`). The included profile is never copied into `aircraft.json`, so a later release's replaces it, except:

- **Redo** runs the setup from the included profile and saves the result in `aircraft.json`, which is used from then on. `setupReset` removes it, and the included profile applies again.
- **Never for this aircraft** keeps the included profile's controls in `aircraft.json`, declined.
- A way that worked in a replay where the one before it didn't (`control profile: the … with … first from now on in this session`) goes first only until the sim closes.

At startup the log says `loaded the package's profiles/aircraft.json (N aircraft control profile(s); M of those aircraft have their own in aircraft.json, which is used instead)`, or `no control profiles included in the package`, and for each aircraft `aircraft key …: included control profile …` when it uses one.

## Work folder

`%APPDATA%\Microsoft Flight Simulator 2024\WASM\MSFS2024\betterreplay-recorder\work\` (Steam). That folder holds:

- `YYYY-MM-DD_HHMM_<takeoff|landing|manual>.rpl`: one file per clip, timestamped in **UTC**.
- `index.json`: the library (event, date, aircraft and its `aircraft.cfg` path, airport, duration, touchdown VS, peak G, bounces). If it's lost, it's rebuilt from the clip headers. An index from before it stored the paths (version 1) gets them from the clips once, at startup (`index: aircraft paths read from N of M clip(s)`).
- `aircraft.json`: the control profiles, one per aircraft: for each control its state (`ok`, `failed`, `automatic`, `skipped`, `absent`, `pending`), method and variable, and where one method doesn't do both ways, each direction's ways in the order they're tried; the throttle lever's calibration, and the spoilers' where their event needed one (see [Control setup](#control-setup)).
- `betterreplay.log` and `betterreplay.prev.log`: the module's log for this and the previous sim session.

## Logging

Every line is prefixed `[BetterReplay]`. In DevMode, open the Console and filter on it. Debug builds (`-Configuration Debug`) also log commands, freeze confirmations and light events. A status heartbeat is logged every 60 s. [MANUAL_TEST.md](MANUAL_TEST.md) lists the lines to expect at each step.

The module also writes every line, with a UTC timestamp, to `betterreplay.log` in the [work folder](#work-folder). You don't need DevMode or the console for it. Each sim start begins a new file and keeps the previous session's as `betterreplay.prev.log`.

For problems the log can't show (how the aircraft moves or sounds frame by frame in a replay), set `kPlaybackTrace` in [src/module/SimBridge.h](src/module/SimBridge.h) to `true` and rebuild: each replay then writes `trace_<clip>.csv` to the work folder (`trace_<clip>_2.csv` and so on for later replays of the same clip), a row per frame with the velocities written against what the aircraft shows, airspeed, engine thrust, N1/N2, the throttle sent, the replay's clock (the real time since the last frame against the step the replay took, the sim's own time, and the module updates since the last frame), g and the control surfaces, and ground speed and height.

## Known gaps

None of these could be verified without running the sim. Each is covered by a step in MANUAL_TEST.md.

- **SDK samples not installed.** The InGamePanels XML and package definition follow a dev-forum example plus the sim executable's own property names, not an SDK sample. If the panel doesn't appear, compare them against the SDK's InGamePanel sample.
- **Reading the package folder.** The included profiles are read from the package folder, trying `\profiles\aircraft.json`, `/profiles/aircraft.json` and `profiles/aircraft.json` in turn; which spelling the runtime takes is untested. Look for `package file: '…'` in the log. If it says `no control profiles included in the package` while the package has the file, none of them worked.
- **No MSFS2024 VS toolset.** Builds use the SDK's clang directly, with the same exports and version library as a working 2024 module. The VS project has never been built.
- **SimConnect dispatch in WASM.** `SimConnect_CallDispatch` is called once at init. If no messages arrive within 2 s, the module falls back to calling it every frame and logs that.
- **Freeze event parameter is undocumented.** `FREEZE_*_SET` is sent with 1/0 and verified through `IS … FREEZE ON`. If it didn't take, the module sends `FREEZE_*_TOGGLE` and logs it.
- **Flaps, spoilers, surfaces and throttle levers** are written every frame via simvars. Aircraft systems, especially complex add-ons that animate from their own LVars, may override them during playback. That's what the future LVar recording is for. At the end of each playback, the module logs which channels the aircraft overrode.
- **Aircraft input events.** Many 2024 aircraft built on the Asobo templates keep their cockpit controls in input events (`B:` vars) and overwrite the simvars from them. The A320neo V2 ignores the throttle, gear, flap and spoiler simvars and the gear key events. So the module also records these input events where the aircraft has them, by name (`ENGINE_THROTTLE_1..4`, `LANDING_GEAR_GEAR`, `HANDLING_FLAPS`, `HANDLING_SPEED_BRAKES`), and replays them through each one's `<NAME>_SET` preset (`fsVarsBVarCall`), the same path a cockpit click or hardware binding takes. Writing the value directly (`SimConnect_SetInputEvent`) doesn't run the aircraft's code, and the A320neo V2 simply recomputed it. Values are recorded as reported (the A320's throttle in percent: 0 full reverse, 16.7 idle, about 86 at TOGA) and scaled to the 0..1 fraction the preset takes, or converted to the range it takes (the FSS E-Jets' throttle: `value * 2 - 1`, a profile's `scale` and `offset`; see the control setup). While one is replayed, the simvars it drives aren't written. After each flight load the log lists which of them the aircraft has, and every input event name at debug level.
- **Overridden controls.** If the aircraft keeps overriding flaps, spoilers or a control surface for half a second, playback stops writing that channel for the rest of the clip, so the two don't fight (flicker), and logs it. Likewise, if the gear snap is undone by the aircraft, the gear isn't snapped again on that aircraft.
- **Control surfaces on fly-by-wire aircraft (open).** The iniBuilds A380 and the Synaptic A220 override the ailerons, elevator and rudder in replays, so playback leaves them to the aircraft (*Overridden controls*) and they don't follow the clip. Test builds tried more on the A380, and none of it worked. Written directly (`fsVarsAVarSet`), its surfaces still went back to its own within 19 s. Its model's animation L:vars (`ELEVATORS_HSTAB_1_ANIMATION` and `_2_`, `RUDDER_ANGLE_ANIM`) follow its own surfaces, and writing the clip's into them only flickered: the A380 sets them again every other frame. Why it holds them where it does: frozen in the air, the load factor its fly-by-wire reads sinks from about 1.0 to 0.55 (the clip's stays near 1.0), so it orders full nose-up and the elevator stays at 18°. Its rudder sits at 10 to 30°; the cause isn't known yet. So the fix has to make its fly-by-wire see what the clip had, not write the surfaces. Next: record the clip's air data (angle of attack, sideslip, IAS and TAS, wind, weight) and compare it with what the A380 reads in a replay.
- **Throttle** (aircraft without throttle input events) is written as the lever simvars, and the hardware throttle is blocked by masking the standard throttle events. Many 2024 aircraft handle the lever themselves: their input events intercept the hardware before SimConnect masking sees it, and they overwrite the simvar. When playback sees the aircraft overriding the throttle simvar, it switches to sending `THROTTLEn_AXIS_SET_EX1`, the same events a hardware axis sends, and logs it. That mode can't block the hardware lever, so leave it alone while a clip plays.
  - Some aircraft don't put the lever position in that simvar. The A320neo V2's value climbs slowly during the takeoff roll, which looks like its thrust command rather than the lever. Replaying it still approximates the lever, but exact detents need the aircraft's own variables (the LVar work).
- **Reversers** are recorded per engine (`GENERAL ENG REVERSE THRUST ENGAGED`, plus `TURB ENG REVERSE NOZZLE PERCENT` for analysis). The engaged flag isn't settable, so playback sends `SET_THROTTLEn_REVERSE_THRUST_ON/OFF`, and the reverse amount is the negative throttle lever. In axis-event mode, the axis carries the reverse amount once the aircraft reports its reverser engaged, scaled to its `THROTTLE LOWER LIMIT`. Aircraft with a control profile reverse the way its setup found instead (see *Reverse in replays* under [Control setup](#control-setup)), including those that set no reverse flag at all. At the end of each playback, the log says whether the lights and reversers followed the clip.
- **Gear** is replayed as commands, not positions, because writing gear positions every frame made the gear flicker. The command comes from when the *recorded gear positions* start moving, since some aircraft (e.g. the A320neo V2) only update `GEAR HANDLE POSITION` once the gear has finished moving. Playback sends `GEAR_SET` plus `GEAR_UP`/`GEAR_DOWN` and lets the sim animate the gear. After play, seek, replay and stop, the gear (and lights) are resent and the gear positions are snapped for a moment, so a jump starts with the gear where the clip has it. If the aircraft moves the gear back itself, the log says so; when stopping on the ground, the aircraft then stays frozen until the gear is at least as far down as before the replay, 20 s at most (`EngineConfig::restoreMaxSec`; the A350's gear takes about 16 s from fully up). A snap that held only counts as the aircraft taking it if it moved the gear (`playback: the gear snap moved the gear and held; this aircraft takes it`): the PMDG 737's held at the start of a takeoff replay, where the gear was down already, and Stop, trusting it, unfroze the aircraft on the ground with its gear still coming down.
  - Aircraft that ignore all of these events need their own gear input event. The module logs a warning if the gear doesn't respond, and lists the aircraft's gear- and throttle-related input events after each flight load.
- **The parking brake** is replayed like the lights (`pbrake`, `BRAKE PARKING POSITION`, sent with `PARKING_BRAKE_SET`; the simvar isn't settable). A replay started parked used to keep it set: the brakes worked against the velocities written every frame, so the aircraft (frozen) didn't slow but the sim's acceleration did, and ChasePlane's head movement, which follows `ACCELERATION BODY X/Y/Z`, showed hard braking all through a taxi. Releasing it by hand mid-replay stopped it at once. Clips recorded before the channel replay with it off; Stop sets it back. Look for `playback: PARKING_BRAKE_SET 0` at the start and `PARKING_BRAKE_SET 1` after Stop; an aircraft that ignores the event shows `playback: pbrake (BRAKE PARKING POSITION) didn't follow the clip in N% of frames`. On the iniBuilds A380 a takeoff replay started parked let go of it, the head movement was right again, and Stop set it back; a takeoff recorded with it set and let go of 7 s in replayed that way.
- **Getting the aircraft ready before a jump.** When Play or a seek jumps, what the clip starts with that takes the aircraft time is got ready first, all at once, with the aircraft frozen where it is; then it jumps and the replay runs. Meanwhile the panel shows *Getting the aircraft ready* in place of the replay controls: a line for each step this jump needs, its ring turning until it's ticked, and a Cancel button. The aircraft is given the clip's speed meanwhile (its body velocities from the clip's start, written every frame), so its systems see the speed the clip starts at, but not on the ground when the clip starts faster than 30 kt (its flaps are then set after the jump, below). Look for `playback: getting ready before the jump (gear down, flaps out), frozen where the aircraft is at the clip's speed (… kt IAS; the clip … kt over the ground)` and `playback: ready after N s (… kt IAS); going to the clip`.
  - **The gear,** when the jump goes onto the ground with the gear down while the aircraft's is up. On aircraft where the gear can't be snapped into place (the A320neo V2 animates its own), lowering it after the jump puts the extending gear into the runway and it stops half way. 50 s at most, the gear command repeated, or the profile's next way of lowering it tried, if it hasn't started. (Unfrozen made no difference on the PMDG 777: it only needed the right way of lowering its gear, which moves frozen.) Stop lowers it the same way before putting the aircraft back on the ground. Look for `playback: lowering the gear before going to the runway` and `gear down after N s`.
  - **The flaps,** driven by the control profile or an input event, when the handle is in another detent from the clip's, and from where the clip's flaps are on their way to: the end of the movement they're in at the jump (still for 1 s, turned back, or the clip's end). The PMDG 777's handle index follows its flaps, so a landing that starts with them still going to 30 has the handle at 25, though the pilot's lever is at 30; an aircraft at 30 waited 15 s for flaps 25 that its lever, driven ahead of the clip at 30, never gave. Look for `playback: the clip's flaps are on their way to where the aircraft has them (…, handle …, there N s in); not waiting for them`. Some aircraft pick the flap setting from the lever *and* their speed: the A320neo V2 gives 1+F (slats and flaps) for lever 1 on the ground, but CONF 1 (slats only) when the lever moves while fast. So the lever waits until the aircraft shows the clip's ground speed (within 20 kt) for 1.5 s (5 s at most), then the flaps until they're there: the surfaces within 2% of the clip's, or still for 3 s with the handle at the clip's index (its setting can differ, as above), or not moving for 15 s; 90 s at most. The PMDG 777's flaps take about ten seconds a detent. Look for `flaps: the aircraft settled after N s (… kt over the ground, the clip …; … kt IAS); moving the flap lever` and `playback: the flaps are where the clip has them (…) after N s`.
  - **The engines, after the jump,** where a turbine's N1 is more than 5% off the clip's and the throttle is replayed by the profile, input events or axis events (not as simvars): the replay holds at its start (as for the flaps below) with the throttle where the clip starts, until each engine is within 3% of the clip's N1 or has held steady for 3 s, 40 s at most. Not into reverse: a jump into deployed reversers leaves the engines to the replay. Look for `playback: holding at the start until the engines are where the clip has them`, then `playback: the engines are where the clip has them after N s (N1 …)` or `… have settled after N s, short of the clip (N1 …)`. They were got ready before the jump at first, with the gear and flaps; but frozen in the air at a takeoff clip's 0 kt the PMDG 777's autothrottle engaged itself again after the disconnect, and held 106% N1.
  - **Flaps after the jump,** where they couldn't be set before it (on the ground with the clip faster, or the velocities can't be set directly): the replay holds at its start instead, frozen there, its position, attitude and velocities written every frame and the playhead still, with the same waits (the lever's counting on the ground or not too). Look for `playback: holding at the start until the flaps are where the clip has them`. Stop puts the profile's flaps back with the lever's wait; with `FLAPS_INCR`/`FLAPS_DECR`, a notch at a time until the lever is back where it was (10 s at most, `playback: the flap lever isn't back at N after 10 s` if not). If the flight ends or another loads first, that's dropped (`playback: the flight ended; not putting the controls back`). A lever already in the right place with the wrong setting (e.g. CONF 1 at lever 1 from a previous approach) isn't corrected.
  - On the PMDG 777 the gear and flaps got ready together in the sim, frozen in the air at the clip's speed, then the replay started (the engines then too, before they moved after the jump). Not seen yet on the Airbus aircraft: whether their warnings and protections react to the clip's speed frozen in the air (about 0 kt for a takeoff clip played from the air: a stall warning; alpha floor with autothrust on), whether the A320neo V2 then gives 1+F at lever 1, and the engines spooling frozen in the air with autothrust on.
- **Engine power under autothrust.** Replaying the lever reproduces the engines where the lever sets the thrust. On the CJ4, N1 stayed within 0.9% of the clip on average. On the PMDG 737, whose autothrottle moves the levers, an autothrottle TOGA takeoff with a later MCP speed reduction replayed as flown (7.1% on average, mostly at the jump). Where the aircraft's own logic sets the thrust with the lever in a detent (the A350 under autothrust in CL), replaying the lever gave the detent's own thrust: climb power down a whole approach, N1 32 to 45% off the clip on average. Those stretches now follow the clip's thrust demand instead (see *Autothrust in replays* under [Control setup](#control-setup)); in the sim, replaying the same A350 landing and approach, N1 was 1.1 to 1.6% off the clip on average. Writing the recorded `TURB ENG N1`/`N2` every frame was tried and doesn't work: the A350, the CJ4 and the PMDG 737 all kept their own N1 (0 of 60 frames held). N2 is still recorded (`n2_N`).
- **Engine diagnostics.** At the end of each playback the log has a line per engine: `playback: engine N N1 was X% off the clip on average (at most Y%) and changed direction Z times a second (the clip: W)`. If the engine hunts (sound "distorted") its direction changes are well above the clip's.
- **The replay's clock.** A replay steps once a frame from the sim's own per-frame update (`module_post_sim_systems_update`), by its frame time: on the A350 at 36 fps exactly 1/36 s a frame, and a hitch as long as it was. It holds while the sim is paused or its time stands still. It used to step from the SimConnect data frames, which land at a different point in the sim's frame each time (the data was a frame stale every other frame or so, and another message comes within the same frame about once a second). Stepped by the sim's time there, a replay at 140 kt moved the aircraft about a metre unevenly every frame, which in the cabin near the engines sounded like the engines spooling up and down two or three times a second; stepped by the real time between data frames, a few squeaks were left where the sim hitched. If the updates stop (three data frames in a row without one), replays go by the real time between data frames again.
  - **Position, attitude and velocities are set directly** (`fsVarsAVarSet`) from that update, rather than queued through SimConnect, which applies them at its own point in the frame. The first 60 frames of each replay check that the aircraft is where it was set: `playback: position, attitude and velocities set directly every frame (N of 60 frames off)`. If it isn't, or a set fails, they go through SimConnect again until the aircraft changes.
  - **Rotation rates.** `ROTATION VELOCITY BODY X/Y/Z` written in radians per second read back 3.28 times (feet per metre) what was written, though what the sim shows in flight is right; a takeoff roll's yaw replayed at 2.1° a second instead of 0.64. They're written scaled by 1/3.28, and each replay checks the rates the aircraft shows against the clip's: `playback: the rotation rates follow the clip (written x0.305)`. If they don't, the scale is corrected and logged.
- **A350 engine whine in replays (open).** On the iniBuilds A350, the higher-pitched part of the cabin engine sound (the fan's whine, not the low roar) sounds distorted in takeoff replays. In the flight itself the whine went away when the thrust came back from takeoff to climb. In the replay it keeps playing, distorted, though at the lower N1 it shouldn't be playing at all. It stops with the EFB's internal engine volume at 0. Ruled out so far:
  - The replay's clock and write timing. Fixed above, which took away most of the earlier squeaks.
  - The aircraft's loading: replayed in the same flight, within 0.2% of the clip's weight and CG, it still did it. Variants are refused now anyway (an A350-900 clip had been replayed on the -900ULR).
  - The thrust: with the takeoff's flex temperature entered, N1 matched the clip to within 0.02% and it still did it. (Without it, the FLX/MCT detent gives MCT: N1 91.2% against the clip's 89.4%.)

  What's known: the A350's `sound.xml` feeds its cabin engine sound N1, N2, `AIRSPEED TRUE`, `GROUND VELOCITY`, `PLANE ALT ABOVE GROUND` and `CAMERA STATE`. In its Wwise soundbank (`inibuilds_aircraft_a350.PC.PCK`) the engine layers take their pitch from N1 and N2 only; their speed, height and camera curves set volume and filters, and the curves that set pitch from speed belong to the gear and rolling sounds. In the replay N1 and N2 change smoothly (0.004% from frame to frame, from SimConnect and from the per-frame update alike), well under a cent of pitch on those curves. Ground speed and TAS are rougher than in the recording (0.02 to 0.1 kt from frame to frame against 0.001), since the physics runs 0 to 3 of its 9.26 ms steps after each write, but the engine's pitch doesn't follow them. The soundbank's curves can be read from the PCK: each RTPC is the FNV-1 hash of its name in lower case (e.g. `simvar_turb_eng_n1`), followed by the property (0 volume, 2 pitch, 3 low-pass), the curve's scaling, its point count and then x, y and interpolation per point.

  Next: find what keeps the whine playing after the thrust comes back: the whine layer's curves from the PCK, against N1, N2, the speeds and the height in the trace (`kPlaybackTrace`).
- **Light key events** are sent with circuit index 0, assumed to mean "all circuits". Not every aircraft takes the sim's light events, so the lights don't replay on all aircraft; at the end of each playback the log says whether they followed the clip.
- **Airports** come from `SimConnect_RequestFacilitiesList_EX1` (the sim's facilities cache around the aircraft), asked for every 15 s and at once on liftoff and touchdown, and kept for the whole flight. Look for `airports: N around the aircraft` after a flight loads, and `, at YMML` at the end of a takeoff's or landing's `saved` line. If that never appears, the list isn't reaching the module and rows show the aircraft alone.
- **Control setup.** It has run in the sim on the PMDG 777 and 737, the iniBuilds A350 and A380, the Synaptic A220 and the FSS E190 (see the status at the top); what hasn't been seen yet is below. Each of these logs what it found:
  - **Aircraft identity** is the path from `SimConnect_RequestSystemState("AircraftLoaded")`, falling back to the title. Profiles go by its family (see [Control setup](#control-setup)); replays need the exact path, so a clip doesn't replay on another variant or preset. Look for `aircraft path: …` and `aircraft key …`: if two variants should share a profile but get different keys, their folders are named differently from the PMDG's and A350's. Clips record the path; older clips without it are matched by the aircraft's title.
  - **Watching input events** reads them with `fsVarsBVarGet`. If that can't read them, only L:vars are found by their movement. Look for `setup scan: N input event(s), M of them readable` (on the A350, 818 of its 829).
  - **Key events** are sent from WASM with `fsEventsTriggerKeyEvent` (not SimConnect, where the throttle axis events failed on the A320neo V2). They act like moving the hardware, so they're only sent when the value really changes (no periodic resend).
  - **Throttle with key events** replays the pilot's hardware axis (`thr_axis_N`), recorded from the throttle key events the module sees (`fsEventsRegisterKeyEventHandler`), so the lever lands where it was, detents included. The lever simvar isn't the lever on every aircraft: on the A320neo V2 under autothrust it's the thrust demand, so CLB replayed as TOGA. Clips without the axis (older ones, or before the hardware first moved) fall back to the simvar. Look for `throttle hardware: key event …` after you first move the throttle; if it never appears, the aircraft takes the hardware another way.
    - On the A320neo V2 it never appears: its hardware throttle doesn't come through as key events the module can see, so its clips have no `thr_axis_N`. With the throttle lever set up (see [Control setup](#control-setup)) they replay the lever's own L:var through its calibration; look for `control setup: throttle lever calibrated: … detents …` and, on playback, `controls: throttle levers from L:var …`. Without it they replay from the simvar: since each key event makes the aircraft re-evaluate its lever (and the engine sound follows), a change in the simvar of 2% or more goes at once, and a smaller one only once it has lasted 30 frames.
  - **Ways for each direction.** The setup's test of the way back has run in the sim: on the A350 the gear key events brought the gear back from where you left it (`control setup: … brought the gear back from where you left it`), and its flaps were saved with two ways back. Playback's switching from one way to the next hasn't been seen yet. Look for `controls: the gear went down with …` in replays.
  - **The gear above the runway** has run in the sim on the A350: held 45 ft above where it stood (15 ft above the ground there, plus 30), it counted as airborne after half a second, its gear went up and came back down while frozen there, and it was put back on the runway with the gear down. Not seen yet on an aircraft whose gear won't move frozen (frozen in the air before a jump, the A380's didn't come down; see *Getting the aircraft ready before a jump* above). There the setup waits for a takeoff instead, or, if the gear goes up but not down, asks you to lower it and won't put the aircraft back until it's down or you cancel; it can't lower it itself. Look for `control setup: the aircraft counts as airborne above the runway`, `can't set up the gear above the runway: …` and `the gear isn't down after 30 s (at …, its handle at …)`.
  - **Simvars** are written with `fsVarsAVarSet`, with the index (`:1`) passed as a parameter.
  - **L:var channels** (`lv_*`) are only recorded on aircraft whose profile chose an L:var, or (`lv_thr_N`) found the throttle lever's own.
  - **Readings the checks use:** `TURB ENG N1`, `GENERAL ENG RPM`, `SPOILERS LEFT POSITION`, `ENGINE TYPE`, `BRAKE PARKING POSITION`, `ON ANY RUNWAY`, `GENERAL ENG COMBUSTION`, `IS GEAR RETRACTABLE`, `SPOILER AVAILABLE`, `FLAPS NUM HANDLE POSITIONS` and `LEADING EDGE FLAPS LEFT PERCENT` (the slats). N1, RPM, spoiler position and the slats are also recorded in clips (about 0.6 MB more per 5 minutes).
  - **Parking brake:** if the aircraft's doesn't set the simvar, the throttle step waits on "Set the parking brake". **Continue anyway** carries on.
